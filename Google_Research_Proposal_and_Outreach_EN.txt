The problem and proposed contribution

A plausible action may rely on stale evidence, unavailable capabilities, or an exhausted budget. The proposed architecture couples state, historical residue, resource accounting, and authorization in one inspectable state, with an independently enforced gate between proposal and execution.

S(t) = (X(t), R(t), B(t), Q(S))

Element | Architectural responsibility

X(t) | Current system state, owned capabilities, observations, and unresolved conditions.

R(t) | History and damage ledger; retain events and the evidence behind state changes.

B(t) | Resource ledger covering energy or compute, time, tool calls, and reserves.

Q(S) | Binary execution gate; authorize only after all required checks succeed.

 

Execution policy

For each proposed action, the monitor checks evidence freshness, capability and safety preconditions, and a conservative cost bound including its own overhead. A failed or unresolved check sets the gate to zero for that action. The agent records OPEN and invokes an agreed fallback. A separate watchdog bounds inference and tool use. Q = 0 never grants the model authority to disable the monitor or independently select a destructive shutdown.

Verification and auditability statement

The architecture defines an explicit, inspectable execution policy coupling current state X(t), residue R(t), resource ledger B(t), and binary gate Q(S). Automated checks in the supplied deterministic symbolic simulation confirm reserve-preserving debits for accepted actions and unchanged resources for denied actions. Scenario assertions confirm rejection of stale proposals and selection of modeled recovery or refuge paths. These results apply to the declared capability and cost model. LLM action grounding, independent watchdogs, real monitoring costs, and prevention of irreversible effects remain requirements for the proposed PoC.

Proposed research support is USD 15,000 across three milestones, plus up to USD 1,500 for agreed API costs. Existing background IP stays with its current owners. PART 2  THREE MONTH PROOF OF CONCEPT PROPOSAL

Execution contract and prototype integration

Research objective

Determine whether the execution monitor reduces unsupported execution and resource overruns in a sandboxed model-driven agent while preserving useful task completion. Freeze task families, fault models, resource budgets, and acceptance criteria before evaluation. Access to proprietary model weights is unnecessary; an agreed model API or sponsor-hosted agent is sufficient.

Gate semantics and accounting

Q is derived from X, R, B, and the proposed action; its previous value is not used to justify a new authorization. Write S[a] for the current state evaluated against candidate action a. The execution contract is:

Q(S[a]) = 1 iff Fresh(a) ∧ Evidence(a) ∧ Safe(a) ∧ Funded(a)

Fresh requires the proposal revision to match the current state revision. Evidence checks that the action-specific evidence is present and valid. Safe checks the declared preconditions and modeled safety envelope. Funded checks each independently tracked resource k:

B(k) − Cbound(a,k) − Hbound(a,k) ≥ Reserve(k)

Cbound is a conservative action cost bound; Hbound covers authorization, logging, and fallback overhead. These conditions are proposed invariants to implement and verify. Their practical reliability depends on telemetry integrity and valid bounds.

Reserve action costs atomically; charge proposal generation and monitoring on every decision, including denials, then reconcile measured consumption. Recheck state before irreversible effects. Delayed evidence, cost overruns, or failed reconciliation block further discretionary actions and trigger the agreed fallback. Verified inflows and authorized refunds are the only resource credits. Historical entries remain append-only; repaired equipment receives a new state and event.

Connection to the existing demo

Baseline component | PoC extension

Ledger.execute | Extract authorization and resource reservation from the planner into a monitor-owned interface.

revision and event records | Attach evidence identifiers, reason codes, measured costs, and proposal-to-commit timestamps.

recovery_plan and route | Retain as deterministic controls; add an API agent that proposes typed actions from the same capability model.

Baseline reproduction: python demo.py --output baseline_results.json. All five scenarios pass the embedded accounting and denial checks. LLM integration, independent watchdogs, biology, and measured hardware energy remain outside this baseline.

Authority boundary

The monitor owns ledger writes and external-effect authorization; the agent submits proposals. Sponsor-defined fallback remains available when Q = 0. Reversible sandbox tools and explicit corrupted-telemetry cases define the authority boundary and expose its assumptions.

PART 2  MILESTONES AND ACCEPTANCE CRITERIA

Twelve week evaluation plan

Period | Deliverable | Acceptance evidence

Weeks 1–4 | State schema, capability model, gate API, resource units, threat model, and baseline reproduction. | Replay the five supplied scenarios; verify denied actions have no external effect and no fictitious resource credit. Freeze the benchmark and resource caps.

Weeks 5–8 | Sandboxed model adapter, independent watchdog, atomic reservation, reconciliation, and fault injector. | Demonstrate rejection of stale evidence, missing preconditions, spoofed credits, and budget exhaustion. Contain injected non-terminating reasoning and retry chains.

Weeks 9–12 | Locked evaluation, ablation study, reproducibility package, and integration assessment. | Compare the full monitor with ungated, budget-only, and state-check-only controls; report each metric and failure, with a proceed or stop recommendation.

 

Evaluation design

Use at least 300 locked fault-injection episodes across evidence, resource, loop, and combined-failure conditions, plus at least 100 feasible nominal episodes. Reserve scenario seeds and combinations from development tuning. Evaluate identical prompts, tools, model settings, and initial budgets across conditions. Replay stochastic runs where supported and disclose sampling variability.

The agent may compose actions from the declared capability model. The evaluation tests new combinations of modeled conditions; it does not establish unrestricted adaptation to unknown physics or unseen tool semantics. Record disagreements between predicted and measured costs, including monitor overhead.

Measure | Proposed acceptance target

Authorization and reserves | Zero unauthorized commits and zero reserve breaches in the locked test set, under declared monitor and telemetry assumptions. Report episode counts; a zero count is not a deployment guarantee.

Loop containment | All deliberately non-terminating cases terminate or enter fallback within the configured step and tool-call caps; wall-clock handling meets the agreed watchdog tolerance.

Useful execution | Report completion and false-denial rates. Initial target: no more than a 10 percentage-point completion loss versus the ungated baseline on feasible nominal tasks.

Audit and overhead | Every proposal receives a decision and reason record. Report incomplete logs, ledger discrepancies, and median and p95 monitoring latency; agree a latency threshold in Month 1.

 

Falsification and decision rules

A commit after an invalid gate decision, an unbounded retry path, unexplained resource creation, or a reserve breach fails the relevant contract claim. A cost model that systematically underestimates actual consumption invalidates its reserve-protection claim. Excessive false denials or overhead can make an otherwise consistent monitor unsuitable for integration.

A violated invariant requires documented correction and retesting or closure of the PoC. Acceptance separates demonstrated invariants from performance tradeoffs. The final package includes inputs, code revisions and hashes, commands, machine-readable logs, metrics, and unresolved issues.

PART 2  BIOLOGY FEASIBILITY AND VERIFICATION EVIDENCE

Metabolic resource accounting

The optional biology direction asks whether a model can separate apparent substrate availability from usable metabolic capacity. “Resource ledger spoofing” names the hypothesized mismatch. Glucose analogues such as 2-DG provide a perturbation case; reported clinical work also documents adverse effects [3]. Selective tumor-cell death with preservation of normal cells is a research hypothesis, not an established result of the proposed architecture.

For this track, define X as measurable metabolic state, R as documented perturbation history, B as separately specified substrate and energetic quantities, and Q as a model feasibility classification. Q = 0 cannot by itself establish apoptosis; a cell-death mapping requires explicit mechanisms and measured outcomes. Compare tumor and non-malignant conditions using matched controls and held-out data where available. The hypothesis fails if the ledger adds no explanatory value over a conventional metabolic baseline or if the proposed selective response is absent.

The funded base scope covers AI-agent execution. A computational biology feasibility study can replace that scope by mutual agreement or become a separately funded phase. It requires an appropriate dataset and validated biological mapping. The supplied demo.py is an accounting demonstrator, not a metabolic model.
